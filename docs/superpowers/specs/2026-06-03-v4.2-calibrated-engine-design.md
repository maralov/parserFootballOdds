# v4.2 — Калібрована прибуткова машина (design spec)

**Дата:** 2026-06-03
**Гілка:** v4.1 → v4.2
**Автор:** brainstorming session (Claude + користувач-експерт)

## Контекст і проблема

Система прогнозує два протилежні треки на матчевий тотал за лайв-аналізом
кандидатів 0:0:

- **Лінія A (TM 0.5)** — матч завершиться 0:0. Точки рішення 60-75'.
- **Лінія B (TB 0.5)** — буде ≥1 гол. Точки рішення 80-90'.

### Симптоми (з логів `data/logs/2026-05-09…13`)

| Період | Сигнали | Результат |
|---|---|---|
| v4.0 (5-10, історія) | 33 ставки | 13 HIT / 16 MISS ≈ **45%** — збитково при коефі 1.6-2.0 |
| v4.1 (5-12, 5-13) | **0 сигналів** за дві доби | гейт ріже все |

### Кореневі причини (ранжування)

1. **P0 — зламаний гейт.** Промпти змушують AI самостійно вирішувати BET/SKIP
   і застосовувати поріг `confidence<0.65→SKIP`. AI завжди скидає в SKIP
   (`gpt-4o` стабільно повертає `confidence=0.6`). EV-гейт ніколи не «пропускає» —
   ріже сам AI. У логах причина завжди `decision_not_bet`, `ev=null`.
2. **P0 — немає калібрування.** Пороги `DS_THRESHOLD_AI=60`, `PS_THRESHOLD_AI=60`,
   `evMin=1.10`, `confidenceMin=0.65` взяті зі стелі. Немає Brier/ROI метрик —
   неможливо знати, чи покращення реально допомагають.
3. **P1 — одноразовий лок.** Рішення фіксується на першому снепшоті 60'/80'
   і не перезапускається на 65/70/75 (TM) чи 85/88 (TB), хоча DS/PS дрейфує ±15-20
   за 5 хв, а коеф TB зростає 1.9→3.0.
4. **P1 — неточний скоринг.** `dryFromCards` повертає `null` при 0 карток
   (втрата ваги); 75% ваги PS на останніх 5 хв (волатильність); `favorite_pressing`
   визначає фаворита за пре-матч 1X2 через 80 хв гри.
5. **Сховище.** `matches.json` — 11.7 МБ/день на 123 матчі. Снепшоти тримають
   `cumulative`+`since2H`+`delta` (3× дублювання); статика дублюється з
   `enrichment.json` (~564 КБ/день); весь файл перезаписується на кожен снепшот
   (`DEBOUNCE_MS=0`).
6. **Мертвий код v4.0** (`src/pipeline/aiDryGoalExpert.js`, `test/aiGate.test.js`)
   та git-сміття (`results/`, `csv/`, `matches copy.json`).

## Мета

1. Система знову видає сигнали і **вимірюється** (Brier/ROI).
2. Сигнали стають прибутковими (відкалібровані пороги, чесні ймовірності).
3. Сховище вдвічі-втричі легше, запис O(1).
4. Розширення на трек 1H — після позитивного ROI на 2H.

## WS-1 · Якість прогнозів

### P0b — Replay/калібрувальний гарніс (keystone, будуємо першим)

Новий `scripts/predictionReplay.js`:

- **Вхід:** діапазон дат → читає `matches.json` (snapshots[] + final).
- **Режими:**
  - `--logged` (default): застосовує гейт до **вже залогованих** AI-виходів
    (`predictions.tm05.ai`, `predictions.tb05.ai`) — без платних викликів.
  - `--recompute-scores`: переобчислює DS/PS поточними формулами.
  - `--fresh-ai`: повторні AI-виклики (платно, для A/B моделей).
- **Метрики per трек / ліга / хвилина:**
  - Hit-rate, Brier score, log-loss (калібрування ймовірностей).
  - ROI@flat (фіксована ставка), ROI@Kelly (frac-Kelly за `ev`).
  - Розподіл фаз (skipped_by_ds, gate_blocked, signal, …).
- **Вихід:** `data/logs/<range>/replay-report.json` + читабельний stdout.

Цей гарніс — критерій приймання для P0a/P1b/P2: будь-яка зміна порогу чи формули
валідовується тут до мержа.

### P0a — Розв'язати AI та EV-гейт

**Промпти (`tm05Prompt.js`, `tb05Prompt.js`):**
- Прибрати рядки `"decision=BET тільки якщо p×коеф≥1.10"` і
  `"confidence<0.65→завжди SKIP"`.
- AI повертає **лише** калібровану ймовірність + `confidence` + `reasoning` +
  `key_signals`. Поле `decision` лишається опційним для діагностики, але **не
  впливає** на гейт.

**Схеми (`tm05Schema.js`, `tb05Schema.js`):**
- `decision` стає optional (default `null`); обов'язкові — `p_*` і `confidence`.

**Гейт (`evGate.js`):**
- Прибрати hard-cutoff `decision !== 'BET'`.
- `confidence` стає **м'яким штрафом**: `pAdj = base + (p − base) × confidence`,
  де `base` — історична baseline ймовірність треку (з гарніса; стартово
  TM05≈0.45, TB05≈0.30). Тобто низький confidence стягує `p` до базової лінії.
- Рішення: `pass = (pAdj × odds) ≥ evMin`.
- Лишити захисти діапазону (`p∈[0,1]`, `odds>1`).

**Контракт повернення** не змінюється (`{pass, reason, ev}`), додається `pAdj`.

### P1a — Зняти одноразовий лок для негативних фаз

У `runTm05Decision.js`/`runTb05Decision.js` та `snapshotCollector.js`:
- Re-evaluation дозволена поки
  `phase ∈ {ds_computed, skipped_by_ds, ai_error, gate_blocked, stats_not_detailed}`.
- Лок (`already_decided`) тільки на `signal` / `goal_during_decision`.
- **Захист від повторних платних AI-викликів:** кешувати AI-вихід у
  `predictions.<track>.ai` з `requestedAtMinute`; повторно звертатись до AI не
  частіше ніж раз на N хвилин (env `LIVE_AI_REEVAL_MIN_GAP_MIN`, default 10).
  Гейт переобчислюється щоразу на свіжому коефі/скорі дешево.

### P1b — Виправити скоринг

`drynessScore.js`:
- `dryFromCards`: 0 карток → повертати `0` (не `null`).

`pressureScore.js`:
- Зменшити сумарну вагу `*_delta_10` компонентів з 75% до ~40%.
- Додати `cumulative_2H` компоненти (накопичений тиск з HT): `xg_2h`, `sot_2h`,
  `big_chances_2h` через `since2H`.
- `presFromFavoriteOddsDisparity` → `presFromLiveDominance`: фаворит за
  **live-домінуванням 2H** (cumulative xG/SoT/touches), а не пре-матч 1X2.

`runTb05Decision.js`:
- `findSnapshotByMinute`: `if (bestDiff > 10) return null`.

Обидва треки:
- `statsLevel !== 'detailed'` з hard-fail → soft: `basic` дозволений з вищим
  порогом DS/PS (env `LIVE_PRED_BASIC_DS_MIN`, default 70).

### P2a — Hardening гонки на гол

Перед dispatch `signal`: свіжий fetch header АБО перевірка
`tracking.firstGoalMinute > snapshotMinute`. Якщо гол стався в проміжку
[snapshotMinute, now] — фаза `goal_during_decision`, сигнал не йде.

### P2b — A/B моделі

Через гарніс `--fresh-ai`: gpt-4o vs gpt-5 / claude-sonnet-4 на історії,
порівняння Brier/калібрування. Перемикач `LIVE_AI_MODEL` уже існує.

## WS-2 · Оптимізація сховища (повний split)

### Drop derived зі снепшота

Снепшот зберігає лише `cumulative` (+ minute/observedMinute/score/possession/
capturedAt/statusText). `since2H` і `delta` обчислюються **на читанні**:
- Новий `hydrateSnapshot(match, snap, prevSnap)` у `matchStore` (або
  `tracker/deltaCalculator`), що повертає снепшот з доданими `since2H`/`delta`.
- `getMatch`/`getLastSnapshot` повертають **сирі** снепшоти; скорери та промпти
  отримують гідратований view через явний виклик або через
  `getHydratedSnapshots(matchId, date)`.

### Split статики

`statistics`, `enrichmentTabs`, `h2h`, `standings` **прибрати** з match-record.
Вони вже є в `enrichment.json`. Додати в `enrichmentStore` геттер
`getEnrichment(matchId, date)` (тонка обгортка над `readEnrichmentStore(date)` з
lookup по ключу — store має форму `{ [matchId]: item }`). При побудові промпта
`runTm05/Tb05Decision` лінива fail-soft підгрузка через цей геттер:
- якщо enrichment недоступний/пошкоджений — промпт будується без турнірного
  контексту (web_search компенсує).

match-record лишає: `matchId, teams, country, league, matchUrl, odds, statsLevel,
baseline1H, tracking, snapshots, final, derived, predictions`.

`baseline1H` лишається в record (похідний, потрібен скорерам кожен снепшот).

### Write-path

`MATCHSTORE_DEBOUNCE_MS` default → 2500 (зараз 0). `flushSync` на finalize/
shutdown уже реалізований. Запис стає O(1) амортизовано замість O(file)/снепшот.

**Очікуваний ефект:** ~11.7 МБ → ~3-4 МБ/день.

## WS-4 · Трек 1H (ТБ/ТМ 0.5 першого тайму) — будуємо ПІСЛЯ прибуткового 2H

Окремий паралельний трек, перевикористовує гейт+AI-інфраструктуру:
- **Кандидат:** 0:0 на ~25-30'.
- **Тригери:** снепшоти 25-30' і 38-43'.
- **Дві лінії:** 1H TM 0.5 (тайм завершиться 0:0), 1H TB 0.5 (≥1 гол у таймі).
- **Власна odds-table** (`oddsTable1h.js`) + DS/PS-варіанти під патерни 1H
  (`drynessScore1h.js`, `pressureScore1h.js`).
- Перевикористовує `evGate`, `aiClient`, нові промпти/схеми 1H.

**Залежність:** P0a (звільнений гейт) + P0b (гарніс) мають бути готові й
відкалібровані до старту WS-4.

## Залежності та порядок

```
WS-2 (storage)  ─┐ незалежні, паралельно з WS-1
WS-3 (hygiene)  ─┘
WS-1: P0b (гарніс) ──► P0a (гейт) ──► P1a+P1b (лок+скоринг) ──► P2 (A/B, hardening)
                                                                    │
WS-4 (1H трек) ◄─────────── після позитивного ROI на 2H ────────────┘
```

## Критерії приймання

- **WS-1:** гарніс рахує Brier/ROI; на історії 5-09…13 система видає >0 сигналів;
  ROI@flat на бектесті ≥ 0 (ціль — позитивний після калібрування).
- **WS-2:** `matches.json` ≤ 4 МБ/день; усі тести проходять; гідратовані снепшоти
  бітово збігаються зі старим збереженим `since2H`/`delta` на регрес-семплі.
- **WS-3:** репозиторій без `results/`/`csv/`/мертвого коду; `matchDigest.js`
  друкує читабельний дайджест за день.
- **WS-4:** обидві лінії 1H видають сигнали; гарніс показує калібрування не гірше
  за 2H.

## Поза скоупом (YAGNI зараз)

- Live-odds fetch замість фіксованої таблиці (окремий проєкт — великий обсяг
  скрапінгу). EV рахується на нормативній таблиці, ризик розбіжності документуємо.
- Blacklist ліг за історичним hit-rate (з'явиться природно з гарніса пізніше).
- Kelly-staking у проді (поки тільки в гарнісі як метрика).
